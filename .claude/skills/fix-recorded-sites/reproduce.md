# Decisions already made, and how to reproduce a row

Moved from SKILL.md sections 0a and 1 (15 Oct 2026); the live-confirm steps are gone: a fix is confirmed offline.

- **Do not ask the owner about these, they are decided:**
  - An open written question that nothing given answers ("why us", cover letter) is an **expected hold**: the AI returns it as category `written` with value `""`, the pool verdict counts it expected, it is never drafted, typed or invented. Any other left field still makes a shortfall.
  - A click on a typeless button is not a "submit press" (explicit `type=submit`/`image`, the form's submit event, or the Submit-words floor only). A script-submit button with another label is a known, accepted gap (`gaps-after-round.md`).
  - An account-first site (sign-up page, SuccessFactors) is a documented hold, not a fill failure.
- **Order of proof, fastest first:** (1) the unit test that fails first and the 3 real asks of the app's AI; (2) the row's FRESH capture replayed offline (a differential with `--old` on the same capture and machine, never a verdict against live: offline replay is unverified (spec `docs/superpowers/specs/2026-10-13-capture-once-measure-many.md`: 0 rows matched live; a row with a CV upload, 17 of 39, misses the account judgment after it; compare like with like: a CI capture replayed on a Mac misses page-kind asks from the page width alone, whatever the build)), `cd desktop/e2e && npm run row -- "<row>"` (if there is none, or it says STALE, ask the pool owner/capture session for one capture: one live run, ~1 min; do not hand-build a page instead); (3) the proof that lands with the fix: a ladder fixture for a wrong decision, a hand-made recorded page or widget-zoo page for a field or control, seen failing on the old build (cases cut from captures by `row-to-case` are no longer made: owner, 15 Oct 2026); (4) one live row from your worktree; (5) the pool owner's batch. Never land on a unit-test guard alone.
- **Measure offline first: the network replay** (owner, 13 Oct 2026; spec `docs/superpowers/specs/2026-10-13-replay-by-network.md`). Each row's newest network record
  is replayed with a build (`cd desktop/e2e && node replay-net.mjs <record dir> <out dir>`; every pool row on a schedule: `site-replays.yml`, the nightly beta's gate; 10 rows on PRs that change the apply flow: `site-replays-pr.yml`): the site's own scripts and replies, the live run's kept AI answers, no site, no model call.
  Its numbers count only for a row whose replay is "same as live" (/admin/lab-form-filling "Replay vs live", the PR's job log); any other row is re-recorded live, Mac first (pool skill), never measured live by a fixer on a hunch.
  A row that is not "same as live": read the spec table "Why a row does not replay as live" first (14 Oct 2026): it may be a real regression of the build (coreweave's stall), and then the replay is your reproducer.
  The older snapshot replay (`npm run row`, `npm run measure`) stays a differential only (0 rows matched live, 13 Oct 2026; spec `2026-10-13-capture-once-measure-many.md`): it names which asks a build changes, never a verdict.
- **Time box:** 10 minutes on any stub or replay probe; then use the real capture or tell the coordinator. A hand-made stub cannot tell a bad fix from a bad fixture.
  **30 minutes on one proof step with no yes or no: stop**, land what is tested, tell the coordinator (a replay that disagrees with the live run is a tool gap: `docs/rules/rounds.md` "During").
- **Row cases (`row-to-case`) are no longer made** (owner, 15 Oct 2026). The case holds a real third-party page (scripts, images, fonts, tracking and URL queries stripped, text kept; owner, 11 Oct 2026): **a site that asks for removal gets its case deleted** at once. **Before writing a hand-made recorded page** run `cd desktop && node --test test/recorded-privacy.test.js` on it (no email but `example.*`, no phone, no typed value, no URL query): it failed late and cost 7 minutes.
- **Start from the named cause:** take one cause and its rows from `~/jobadabra-web/tools/site-run.sh node jobs/needs-fix-causes.mjs` (the By-cause tab), not from scratch; the coordinator's brief gives the evidence.
- **When the fix lands, report five lines:** time per step (pick the cause, decide, code and failing tests, real asks, replay/capture, live row, ship), the ladder numbers, and the hash **on origin/main** ("landed" means on `origin/main`, not a WIP commit).

0. **Look at `step-*.png` in order, then `end.png`** (11 Oct 2026; full page, one per page or step reached, replays: `replay-step-*.png` then `end-replay.png`). Every local run keeps the last screenshot of where the extension stopped (local, fake applicant); the step pictures sit beside it: pool `smoke-reports/evidence/<day>/<row>/end.png`, a live row `<capture dir>/end.png`, a saved capture `replay-candidates/<day>/<row>/end.png` (the live run's), an offline replay `<capture dir>/end-replay.png` (`row: end screenshot: <path>`): compare live and replay side by side. A dialog, error banner or empty page over the form shows there at once; a judge answer `blocked` (dialog|error|overlay|gone) in the evidence log points at the same thing. `no end screenshot: <why>` in a verdict is an error to fix first.
1. **ASKED, ANSWERED, DONE before any hypothesis** (owner, 11 Oct 2026: ~40% of each fix went to a wrong first guess). Write three lines from the run's evidence: ASKED (the sketch: buttons listed, candidates, frames, digest flag), ANSWERED (`page kind:` with `formFrame`, the `digest:` line: outcome, verb, numbers, dropped), DONE (what was pressed, where the page went: 54's press trace). A hypothesis that does not explain all three is not a diagnosis; a missing line is step 1.5b. **Read the artifacts, in this order:** (a) `smoke-reports/<day>-<shape>.app.log` (the app's whole log, kept per run; older runs: the e2e app's `jp-e2e-*/logs/app.log` in the temp folder, by time and host):
   `page kind:`, `page kind: none (<error>)`, `ladder:`; (b) the shape's `.log` (the extension's `fill:` lines, the STALL dump with `controls` and `buttons`); (c) `live-frames/*.png` (check the host in the log vs the picture: the folder is overwritten);
   (d) the report's reached step. **Pair each extension line with the app's line for the same request** (an extension answer with no app line: the request never arrived or the extension returned first).
   **`grep` the code for a log message before adding one** (a duplicate was written once).
2. **Only for a row without a network record** (debug with the network replay above first; owner, 15 Oct 2026). **The older snapshot replay (seconds, no site, no AI cost):** `cd desktop/e2e && npm run row -- "<pool row name>"` replays the row's own candidate (its pages, frames, CSS and
   the app's AI answers of that run) on the app's own server under plain node, with the real extension, the fake applicant and memo-only AI (a question the live run never asked is
   reported, never sent to claude -p). It prints the same evidence lines as a live run, `followed N/M live presses` (the site's reaction to each press is played back from the live
   run), and `DIVERGED: press k: pressed "X"; live pressed "Y"` where the extension did otherwise: that line, or the evidence lines matching the live failure, is the repro.
   A fix is first SHOWN here, never proven: the row must now reach further and `--old <old extension/>` must still fail (a differential on the same capture and machine); the live run (step 4) proves it: offline replay is unverified (spec `docs/superpowers/specs/2026-10-13-capture-once-measure-many.md`: 0 rows matched live; a row with a CV upload, 17 of 39, misses the account judgment after it; compare like with like: a CI capture replayed on a Mac misses page-kind asks from the page width alone, whatever the build). `npm run rows` replays every row of the newest day in one browser.
   Its limits: a page the live run never reached cannot be replayed, and a changed ask (a new sketch or prompt) is not in the row's kept answers: confirm live once (step 3).
   **A capture from before the replay format (11 Oct 2026) is refused as STALE** (exit 3, it says so): capture the row once (`npm run record-sites -- --only "<row>"`; it keeps a
   failing row's capture, `RECORD_KEEP_CANDIDATES=1` keeps it either way), then replay. Never debug from a stale capture's replay.
   **`captured with an older applicant seed`** (the capture recorded another e2e applicant, or none: before 9f6ff67): its fill asks miss the kept answers, so its fill
   result is not your fix's; re-capture the row live first. Page kinds and presses still replay.
5. **Prove the repro: two hard rules.** (a) **The SAME signature:** a repro counts only when it shows the same log lines as the live failure (the same `page kind:` and `ladder:` lines); one that fails for another reason proves another bug
   (Datadog: the frame did grow, but the AI had answered "form", which cannot carry `form_frame`, so a real but different blocker came first). (b) **Which blocker?** Before any fix the log must answer it; if it cannot (frame count, `form_frame`,
   digest flag, the named button's flags: `no Apply button to press {found, visible, pickable…}`), add that line, run once, then fix. Also: the stub was really called (count the asks), and the case FAILS on the build before the fix
   (`REAL_EXTENSION_DIR=<old extension/>`); one that passes there is only a guard. **Which layer proves what:** a hand-stubbed AI answer in a recorded page proves the extension handles a CORRECT answer, never that the model gives it
   (that is `ladder-score` and the live pool). A shape that fails once (a moody site) is run twice before it counts.
6. **Offline, no app run, seconds:** `cd desktop && node scripts/stage.mjs` once per fresh worktree (builds `shared/`), then `npm run ladder-score -- --offline --only <fixture>` (what the stored AI answer says) and
   `cd e2e && JP_REPLAY=1 REPLAY_ONLY=<case> node --test test/recorded-pages.test.mjs` (the real extension on a recorded page). The shared e2e page is a queue (the coordinator, `coordinator.txt`): read the offline result and the newest logs first.
